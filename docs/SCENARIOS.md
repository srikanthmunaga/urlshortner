# Scenarios: Decomposition, AI-Assisted Execution, Validation

This document demonstrates the process the assignment asks for: requirement
understanding → task decomposition → AI-assisted execution with traceability
→ validation. Each scenario below is written as it actually happened while
building this prototype.

---

## Scenario 1 — Greenfield: Core shorten + redirect + analytics

**Requirement (as given):** "Build a URL shortener service from scratch with
core APIs, analytics, and reliability features."

### 1. Requirement understanding
This is intentionally broad. I normalized it into concrete engineering
questions before writing code:
- What's the identity of a "URL"? → treat by hash of normalized long URL for
  dedup, not just raw string equality.
- What does "analytics" mean at minimum? → total clicks, recent click
  timestamps, referrer/user-agent, a time-windowed count (24h) as a proxy
  for "trending."
- What does "reliability" mean at minimum, given 2–3 day scope? → caching on
  the hot path, rate limiting on writes, graceful expiry handling, no silent
  data loss on concurrent updates.

### 2. Task decomposition
1. Data model: `ShortUrl` (mapping + metadata) and `ClickEvent` (analytics),
   with indexes on lookup fields — *no dependencies*.
2. Short-code generation strategy (random Base62 + collision retry) —
   *depends on (1)*.
3. Create endpoint: validation, dedup-by-hash, custom alias handling —
   *depends on (1, 2)*.
4. Redirect endpoint: cache-first lookup, expiry/active checks, click
   recording — *depends on (1)*.
5. Stats endpoint: aggregate + recent events — *depends on (1)*.
6. Reliability layer: caching, rate limiting, scheduled expiry sweep —
   *depends on (3, 4)*.
7. Tests: unit (service logic) then integration (full HTTP flow) —
   *depends on (3, 4, 5)*.

### 3. AI-assisted execution (traceability)
- **Generated by AI, accepted as-is:** boilerplate JPA entity getters/setters,
  the `GlobalExceptionHandler` HTTP-status mapping table, MockMvc test
  scaffolding structure.
- **Generated by AI, then edited:** the initial short-code strategy proposal
  encoded the DB auto-increment ID directly (`Base62.encode(id)`). I rejected
  that — it leaks creation order/volume and makes codes enumerable/guessable
  — and redirected to random generation with a uniqueness retry loop instead.
  This is recorded as the rationale comment directly in `Base62Encoder.java`.
- **Rejected outright:** an early suggestion to store raw click IPs "for
  richer analytics." Rejected for privacy exposure with no clear product
  need justifying it; hashed IPs were used instead.
- **Constraints given to the AI up front:** no external dependency unless
  its Maven coordinates could be verified in this environment; every public
  endpoint needs explicit validation; every non-trivial design choice needs
  an inline rationale comment (not just code) so a reviewer doesn't have to
  reverse-engineer intent.

### 4. Validation
- Unit tests cover: unique code generation, duplicate-URL idempotency,
  custom alias conflict (409), unknown code (404), expired code (410),
  click recording increments count and hashes IP.
- Integration test covers the full create → redirect → stats loop against a
  real (in-memory) H2 instance via MockMvc, plus a validation-rejection case
  and a duplicate-alias-conflict case.
- Manual review flagged the cache-staleness-on-expiry trade-off (see
  ARCHITECTURE.md) — this was **not** caught by tests, it surfaced from
  reading the `@Cacheable` interaction with expiry logic line by line. Worth
  noting: AI-assisted generation produced working code here, but the
  cache/expiry interaction risk only became visible on manual re-read —
  exactly the kind of thing engineer ownership is supposed to catch.

## Scenario 2 — Brownfield: Add custom alias support to an existing shorten flow

**Requirement (as given, framed as an enhancement):** "Users should be able
to request a specific short code instead of a random one."

### 1. Requirement understanding
Ambiguity to resolve: what happens if the requested alias is taken? Silent
fallback to random, or explicit error? I chose explicit error (409 Conflict)
— silent fallback would surprise a caller who specifically wanted a
memorable/branded code, which is presumably the entire point of the feature.

### 2. Codebase reasoning (impacted surface)
Working from the greenfield core above as the "existing" codebase:
- `CreateUrlRequest` DTO — needs a new optional field with its own
  validation (length, character set) so bad aliases fail fast with a clear
  message rather than colliding with the auto-generation path.
- `UrlServiceImpl.createShortUrl` — the branch point: alias present → check
  existence, fail or use it; alias absent → existing random-generation path
  unchanged.
- `ShortUrlRepository` — needed `existsByShortCode` (cheap existence check,
  not a full entity fetch) — this didn't exist yet.
- No changes needed to the redirect or stats paths — a custom alias *is* a
  short code once created, so downstream logic is untouched. Confirming
  this (rather than assuming it) is the actual "architectural understanding"
  step: I traced every read site of `shortCode` to confirm none of them
  branch on how the code was generated.

### 3. AI-assisted execution (traceability)
- **Generated, accepted:** the `existsByShortCode` derived query method.
- **Generated, then edited:** first-pass validation regex allowed any
  character; tightened to `[A-Za-z0-9_-]` with explicit length bounds
  (4–16) after considering that aliases become part of a public URL and
  should avoid encoding/interpretation issues.
- **Human sign-off point:** the choice of 409 (explicit conflict) vs. silent
  fallback was treated as a product decision, not a technical one — flagged
  explicitly rather than having the AI (or me) pick silently, since it
  changes observable API behavior for every caller.

### 4. Validation
- Regression check: existing unit tests for the random-generation path still
  pass unmodified — confirms the branch didn't disturb the untouched path.
- New tests: alias conflict → 409 (unit + integration), alias with invalid
  characters → 400, alias within bounds → 201 with the exact alias returned
  as `shortCode`.
- Manual check of the redirect and stats paths against the alias-created
  code, confirming the "no downstream changes needed" architectural
  conclusion from step 2 held in practice.

## Scenario 3 — Ambiguous: "Make sure the service is production-ready"

**Requirement (as given):** deliberately vague — this is the assignment's
"ambiguous requirements" case, and I've treated it as such rather than
picking one interpretation and hiding the ambiguity.

### 1. Requirement understanding — surfacing the ambiguity instead of resolving it silently
"Production-ready" could mean, non-exhaustively: authentication/authorization,
horizontal scalability, observability/alerting, GDPR-style data retention,
SLA-backed uptime, disaster recovery. Building all of these in 2–3 days is
not realistic, and picking one silently would misrepresent scope to a
reviewer. So the engineering response is to **scope it explicitly** rather
than guess:

- **In scope for this prototype, given time budget:** the reliability
  primitives that are cheap and high-leverage — caching, rate limiting,
  input validation, structured error responses, optimistic locking against
  lost updates, a background consistency sweep.
- **Explicitly out of scope, flagged, not silently skipped:** auth/authz,
  multi-instance deployment (shared cache/rate-limit store),
  observability/metrics dashboards beyond Actuator's default health
  endpoint, data retention/deletion policy for click analytics.

### 2. Task decomposition (for the in-scope slice)
1. Identify failure modes: concurrent click-count writes, cache/DB
   divergence on expiry, unbounded creation traffic, malformed input.
2. Concurrency: add optimistic locking (`@Version`) rather than a
   pessimistic lock, since click increments are frequent and short-lived —
   pessimistic locking would serialize the hottest path in the system.
3. Traffic control: rate limit the write endpoint (creation), not the
   read/redirect endpoint — redirects are the product's core value and
   should degrade last, not first.
4. Input validation: reject malformed URLs, oversized payloads, invalid
   aliases at the DTO layer before they reach business logic.
5. Consistency: scheduled sweep for expired-but-active rows (belt-and-braces
   alongside on-read expiry checks).

### 3. AI-assisted execution (traceability)
- **Generated, then substantially edited:** first-pass reliability plan from
  AI defaulted to "add Redis and a message queue." Rejected as
  disproportionate to a 2–3 day prototype assignment — flagged explicitly as
  scope creep, and replaced with the lighter-weight, single-instance
  primitives listed above, with the Redis/queue path documented as the
  *next* step rather than built now (see ARCHITECTURE.md "Known
  Limitations").
- **Human sign-off required and applied:** the decision to rate-limit writes
  but not reads was made deliberately by me, not defaulted to by the AI —
  it directly affects product behavior under load (which requests fail
  first) and needed explicit judgment about which path matters more to
  protect.
- **Quality gate applied:** every new file reviewed for whether it needed an
  inline rationale comment before being accepted, specifically because this
  scenario is ambiguous by design — a future reviewer needs to know *why*
  a boundary was drawn where it was, not just where it was drawn.

### 4. Validation and risk control
- Documented, not hidden: the "out of scope" list above is stated explicitly
  in this doc and in `docs/ENGINEERING_SUMMARY.md` rather than presenting
  the prototype as more production-ready than it is.
- Risk register (abbreviated — full version in ENGINEERING_SUMMARY.md):
  unauthenticated deactivation endpoint (anyone with a code can kill a
  link) is the highest-severity known gap; flagged as the first thing to
  fix before any real deployment.
